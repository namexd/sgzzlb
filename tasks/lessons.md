## 工具行号偏移使用

**问题**：`Read` 工具的 `offset` 参数是行号，不是字符偏移；多次误写为超出文件长度的数值会造成无效读取和任务卡顿。

**解决**：读取文件片段前先用 `grep -n` 或已知文件总行数确认目标行号；如果一次读取提示超出长度，下一次必须立即改用有效行号或改用搜索定位。

**教训**：工具报错后不能机械重复同一调用，必须先修正参数或切换方法，避免浪费上下文和打断长任务节奏。

**复发补充**：如果文件只有几千行，绝不能把搜索结果、字符位置或猜测值直接填进 `offset`；例如不能对 2198 行文件使用 `offset: 4800`，也不能给普通源码文件传 `pages`。本次 P9 中又对普通 Markdown/源码文件传入非法 `pages`，说明读取前必须先判断文件类型：只有 PDF 读取才允许使用 `pages`，普通文本一律只用 `offset/limit`。

**执行规则**：读取片段时先用已知行号范围、`grep -n` 定位或从文件开头小范围读取确认总行数；一旦 offset 报错，下一次必须换成有效行号或改用搜索/脚本定位，禁止复制同一个错误 JSON 参数。

**再次复发补充**：普通源码和 Markdown 读取严禁传 `pages`；如果刚刚因为 `pages` 或超大 `offset` 报错，必须停下来手动重写参数，不能让工具调用沿用上一轮 JSON。`pages` 只给 PDF 用，源码一律只给真实行号 `offset/limit`。

**2026-06-17 强制规则**：普通文本、源码和 Markdown 的 `Read` 工具调用 JSON 只能包含 `file_path`、`offset`、`limit` 三类字段；`pages` 字段只允许 PDF。若上一轮工具因 `pages` 失败，下一轮必须先手动重写整个 JSON，禁止沿用或微调失败参数。

**2026-06-17 Python 写文档教训**：使用 heredoc Python 写入中文 Markdown 时，脚本必须显式声明 `# -*- coding: utf-8 -*-` 并用 `Path.read_text/write_text(encoding="utf-8")`，避免 shell 或解释器按非 UTF-8 处理导致写入失败。


## 接口数据源迁移

**问题**：项目从本地静态 catalog 演进到数据库资料版本后，接口层仍可能在无版本参数时静默读取 `data/catalog.*`，导致线上数据与后台发布版本脱节。

**解决**：所有会变的资料数据（武将、战法、装备、兵种战法）接口必须默认解析数据库 published catalog snapshot；静态 catalog 只能作为开发/测试种子或显式初始化 fallback，生产路径找不到 published 版本时返回明确错误。

**教训**：架构迁移时不能只新增数据库能力，还要收敛旧静态主路径；否则新旧数据源混用会让评分、模拟和后台审核结果不一致。

**问题**：MySQL 中 JSON 字段（如 `generals`、`tactics`）以字符串存储，查询返回时需要手动解析。

**解决**：在 `db.js` 中添加 `parseLineupRow` 函数，统一处理 JSON 字段的解析。

**教训**：使用 MySQL 存储 JSON 数据时，必须在查询层统一处理序列化/反序列化，避免在业务层重复处理。

## 测试数据隔离

**问题**：测试使用共享的 MySQL 数据库，之前的测试数据会影响后续测试。

**解决**：使用唯一 ID（如 `Date.now()`）避免冲突，或在测试前清理数据。

**教训**：集成测试应确保数据隔离，要么使用独立的测试数据库，要么使用唯一标识符避免冲突。

## 用户识别规则

**问题**：多个 API 端点使用不同的用户识别逻辑（`getAuthUser`、`getUser`、混合调用）。

**解决**：创建统一的 `resolveUser` 函数，明确优先级：Bearer token > x-user-id > anonymous。

**教训**：用户认证逻辑应集中管理，避免分散在各处导致不一致。

## 请求日志设计

**问题**：需要记录请求日志，但不想影响性能。

**解决**：使用 `res.on("finish")` 事件记录日志，只记录慢请求（>1s）和错误请求（状态码>=400）。

**教训**：日志记录应异步进行，避免阻塞请求处理；只记录有价值的日志，避免日志泛滥。

## 战报可信度分层

**问题**：用户可能误解少量战报的统计结论。

**解决**：根据战报数量分层（高/中/低/极低），在返回结果中明确说明可信度和样本量。

**教训**：统计数据必须附带可信度说明，避免小样本被误读为确定结论。

## 规则管理版本化

**问题**：规则配置变更后无法回滚，容易造成线上问题。

**解决**：前端维护历史版本列表，支持回滚到任意版本；服务端保存版本号。

**教训**：配置管理必须支持版本化和回滚，避免误操作无法恢复。

## CI/CD 分阶段

**问题**：部署流程没有分阶段，测试失败也会继续部署。

**解决**：将 CI/CD 分为 test、build、deploy 三个阶段，只有前一阶段成功才继续下一阶段。

**教训**：CI/CD 应该分阶段设计，测试失败不应继续构建，构建失败不应继续部署。

## CORS 方法遗漏

**问题**：CORS 配置只允许 GET/POST/DELETE/OPTIONS，缺少 PUT 方法，导致跨域 PUT 请求失败。

**解决**：在 `applyCors` 函数中添加 PUT 到 `access-control-allow-methods`。

**教训**：CORS 配置必须与实际使用的 HTTP 方法保持一致，添加新方法时需要同步更新 CORS 配置。

## 前后端 API 不一致

**问题**：后端实现了多个 API 端点，但 admin 前端缺少对应的调用函数，导致功能无法使用。

**解决**：系统性地检查后端 API 和前端 API 的对应关系，补充缺失的函数。

**教训**：添加新 API 端点时，必须同步更新前端 API 适配层，并确保路由和页面组件也相应更新。

## 数据库查询函数缺失

**问题**：有列表查询但缺少按 ID 查询单条记录的函数，导致详情功能无法实现。

**解决**：为每个主要表添加 getById 函数，支持单条记录查询。

**教训**：数据库层应该提供完整的 CRUD 操作，即使当前不需要，也应该预先实现以备后用。
