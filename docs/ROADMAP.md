# 后续路线图

更新时间：2026-06-03。

## 执行原则

- 先消除回归阻塞，再继续叠功能。
- 先统一数据边界，再扩后台运营能力。
- 前台免费层必须保留完整基础评分能力，高级层只扩深度解释、替代方案和使用上限。
- 所有生产凭据只走环境变量、CI secret 或服务器配置，不写入仓库文档。

## P0：回归基线和安全收口

目标：让项目重新拥有可信的本地验证入口。

- 已完成：本地默认 MySQL 连接可用，本地开发和本地测试共用 `sgzzlb_local`，`npm test` 已能完整跑完 `catalog`、`scoring`、`server`、`drawStorage`。
- 已完成：增加 `.env.example` 和部署环境变量说明，只写变量名和用途，不写真实值。
- 确认历史部署凭据是否需要轮换；如已进入提交历史，按生产安全流程处理。
- 已完成：`src` H5 构建和 `admin` 构建验证通过。

验收标准：

- `npm test` 通过。
- 文档中不再出现真实密码、面板 token、私钥或其它生产凭据。
- 构建命令有明确通过记录。

## P1：统一账号和阵容数据

目标：消除 `.runtime` 与 MySQL 的阵容数据分裂。

- 将 `GET /api/v1/lineups`、`POST /api/v1/lineups`、`DELETE /api/v1/lineups/:id` 统一到 MySQL。
- 前台保存阵容、账号同步、对位页读取保存阵容全部走同一份服务端数据。
- 后台阵容管理读取 MySQL，并保留按用户、时间和分数筛选。
- `.runtime` store 只保留规则草案、资产审核和审计，或进一步迁入 MySQL。
- 增加阵容 API 回归测试，覆盖登录态用户、匿名用户和删除权限。

验收标准：

- 同一用户在评分页保存后，账号页、对位页和后台能看到同一条阵容。
- 同步本地阵容后再次拉取不会丢失或重复。
- 服务端测试覆盖新增存储边界。

## P2：远程模式和抽卡闭环

目标：让 H5/小程序远程模式可以稳定使用。

- 修正 CORS 允许头，确保 H5 Bearer token 请求可用。
- 统一 `x-user-id`、Bearer token 和匿名用户的使用规则。
- 抽卡页从纯本地存储升级为“本地先写、远程再同步、失败有提示”的保守链路。
- 抽卡统计页支持远程数据回填。
- 账号页同步增加冲突提示和失败明细。

验收标准：

- 新用户注册/登录后能保存阵容、记录抽卡、同步、退出再登录仍能找回数据。
- 远程失败时本地数据不丢，页面有明确失败提示。

## P3：后台运营能力

目标：后台从观察面板升级为可运营工具。

- 用户列表和用户详情：订阅层级、阵容数、抽卡数、反馈数。
- 反馈处理：状态、备注、筛选、批量处理。
- 阵容管理：按用户、兵种、评分、时间筛选；删除需要二次确认。
- 抽卡和战报管理：只读统计优先，避免早期误删真实用户数据。
- 规则管理：版本号、启用状态、灰度对象和回滚。
- 审计日志：记录操作者、IP、目标对象和前后值。

验收标准：

- 管理员能完成反馈处理、用户排查和规则查看。
- 高风险操作都有二次确认和审计记录。

## P4：生产部署和监控

目标：把部署从“能上线”推进到“可维护”。

- HTTPS 配置和微信小程序合法域名校验。
- PM2、Nginx、Node、MySQL 的健康检查和日志轮转。
- 数据库定时备份和恢复演练。
- GitHub Actions 增加测试、构建和部署分阶段结果。
- 发布后冒烟：`/health`、前台首页、后台登录、核心 API。

验收标准：

- 每次发布有 CI 结果、部署结果和生产冒烟记录。
- 生产故障能通过日志定位到请求、用户和接口。

## P5：评分和战报模型增强

目标：从规则评分走向可持续迭代的阵容分析。

- 评分规则版本化，记录每次评分使用的规则版本。
- 战报样本去重、可信度分层和隐私处理。
- 对位结论引入真实战报统计，但避免把小样本包装成确定胜率。
- 高级订阅能力扩展为深度解释、更多替代战法、更多保存阵容和更高对位次数。

验收标准：

- 战报统计只在样本量足够时影响结论。
- 用户能看懂“规则推断”和“样本统计”的区别。
