# 后续路线图

更新时间：2026-06-04。

## 执行原则

- 先消除回归阻塞，再继续叠功能。
- 先统一数据边界，再扩后台运营能力。
- 前台免费层必须保留完整基础评分能力，高级层只扩深度解释、替代方案和使用上限。
- 所有生产凭据只走环境变量、CI secret 或服务器配置，不写入仓库文档。

目标：让项目重新拥有可信的本地验证入口。

- 已完成：本地默认 MySQL 连接可用，本地开发和本地测试共用 `sgzzlb_local`，`npm test` 已能完整跑完 `catalog`、`scoring`、`server`、`drawStorage`。
- 已完成：增加 `.env.example` 和部署环境变量说明，只写变量名和用途，不写真实值。

- `npm test` 通过。
- 文档中不再出现真实密码、面板 token、私钥或其它生产凭据。
- 构建命令有明确通过记录。

- [x] 前台保存阵容、账号同步、对位页读取保存阵容全部走同一份服务端数据。
- [x] 后台阵容管理读取 MySQL，并保留按用户、时间和分数筛选。
- [x] `.runtime` store 只保留规则草案、资产审核和审计，或进一步迁入 MySQL。
- [x] 增加阵容 API 回归测试，覆盖登录态用户、匿名用户和删除权限。

验收标准：

- [x] 同一用户在评分页保存后，账号页、对位页和后台能看到同一条阵容。
- [x] 同步本地阵容后再次拉取不会丢失或重复。
- [x] 服务端测试覆盖新增存储边界。

## P2：远程模式和抽卡闭环 ✅

目标：后台从观察面板升级为可运营工具。

- [x] 用户列表和用户详情：订阅层级、阵容数、抽卡数、反馈数。

- [x] 阵容管理：按用户、兵种、评分、时间筛选；删除需要二次确认。
- [x] 抽卡和战报管理：只读统计优先，避免早期误删真实用户数据。
- [x] 规则管理：版本号、启用状态、灰度对象和回滚。
- [x] 审计日志：记录操作者、IP、目标对象和前后值。

验收标准：

- [x] 管理员能完成反馈处理、用户排查和规则查看。
- [x] 高风险操作都有二次确认和审计记录。

### 剩余任务（服务器配置层面）

1. HTTPS 配置：需要在服务器上配置 SSL 证书（Let's Encrypt 或其他）
2. 微信小程序合法域名校验：需要在微信公众平台配置服务器域名
3. 数据库定时备份：需要在服务器上配置 cron 任务备份 MySQL

## 配将功能规划

配将功能将从当前“用户手动输入阵容后评分”升级为“基于用户库存生成可解释阵容建议”。详细需求见 [`lineup-recommendation-spec.md`](lineup-recommendation-spec.md)。

阶段目标：

- P16：生成配将功能需求文档，明确用户场景、一期范围、输入输出、页面交互、接口数据流和验收标准。
- P17：实现一期配将入口，复用 `POST /api/v1/accounts/optimize`、`utils/optimizer.js` 和 `utils/scoring.js`，输出最多 3 套共存阵容。
- P18：接入对位预览和战报模拟复核，展示胜率、战损、稳定性、规则覆盖和估算假设。
- P19：补充高级资产管理、历史推荐方案、反馈闭环和后台运营能力。

边界：配将推荐不是官方隐藏算法，也不承诺真实胜率；结果必须展示资料版本、规则覆盖和估算说明。
