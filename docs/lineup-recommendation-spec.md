# 配将功能需求规格

## 背景与目标

当前项目已经具备可解释阵容评分、对位预览、战报模拟、赛季资料版本和账号库存优化能力。用户后续希望增加“配将”功能，参考同类页面的能力，把“我有哪些武将和战法”转成“我应该优先组哪几队、为什么这么组、还能怎么替换”。

配将功能的目标不是给一个黑盒答案，而是输出可解释、可复核、可继续进入评分/对位/战报模拟的阵容建议：

- 根据用户拥有的武将、战法、红度、赛季和偏好，推荐可用阵容。
- 支持单队推荐和多队共存，尽量避免武将、战法冲突。
- 复用现有评分、短板、替代战法、资料版本、规则覆盖和战报模拟能力。
- 明确资料版本、规则覆盖和估算假设，避免把建议包装成官方隐藏算法或确定胜率。

## 用户场景

1. **库存配将**：用户录入已拥有的武将和战法，希望系统推荐优先组哪一队或哪几队。
2. **共存排队**：用户想同时组 2-3 队，要求关键武将和核心战法尽量不冲突。
3. **缺战法替代**：用户缺少热门战法时，希望知道可用替代战法、替代后的强度变化和短板。
4. **已有阵容优化**：用户已有一队，想锁定部分武将或战法，查看剩余位置怎么补。
5. **赛季/剧本适配**：用户按当前赛季或资料版本查看推荐，避免旧赛季资料影响判断。
6. **对位验证**：用户拿推荐阵容继续进入对位页或战报模拟，查看对常见环境模板的表现。

## 参考页面能力拆解

参考截图中的配将页面需求按能力抽象，不在本阶段锁死视觉细节：

- **资产输入区**：录入或选择武将、战法、红度、赛季、偏好兵种、排除项和锁定项。
- **推荐控制区**：选择推荐目标，例如单队最强、多队共存、偏输出、偏稳健、低战损、按某个兵种优先。
- **推荐结果区**：展示推荐阵容卡片，包括武将、战法、兵种、评分、优先级、核心理由、短板和替代建议。
- **冲突提示区**：展示战法冲突、武将重复、库存不足、资料版本不一致和规则覆盖不足。
- **后续操作区**：支持保存阵容、进入评分报告、进入对位预览、进入战报模拟、复制/分享方案。

无法从截图确认的控件名称、排序、具体文案和视觉样式，在后续 UI 设计阶段再确认；本需求只固定能力边界和数据流。

## 功能范围

### 库存录入

- 武将库存：`generalIds`，后续可扩展红度、等级、兵书、加点、装备。
- 战法库存：`tacticIds`，需要区分已拥有、可兑换、暂缺。
- 赛季资料：`season`、`catalogVersionId`，结果中必须回传 `catalogContext`。
- 偏好条件：目标队数、偏好兵种、锁定武将、排除武将、锁定战法、排除战法。

### 推荐生成

- 单队推荐：从库存中生成评分最高或最匹配偏好的阵容。
- 多队共存：最多生成 2-3 队，默认不复用武将和战法。
- 战法替代：缺少核心战法时给出替代战法和替代风险。
- 冲突说明：输出战法被占用、核心武将不足、兵种适性不足、关键战法缺失等问题。

### 解释报告

每个推荐阵容至少展示：

- 阵容优先级和推荐理由。
- 三名武将、六个战法、兵种。
- 总分、维度拆解、短板、风险提示。
- 战法兼容性、兵种适性、核心联动说明。
- 资料版本、规则覆盖、估算假设。
- 可选替代方案和强度影响。

### 结果联动

推荐结果需要能继续进入：

- 评分页：查看完整可解释阵容评分。
- 对位页：与环境模板或保存阵容做对位预览。
- 战报模拟：对 Top N 阵容做批量模拟复核。
- 阵容保存：保存为用户阵容，供后续复盘和战报统计使用。

## 一期范围

一期目标是把“库存输入 → 推荐 → 解释 → 跳转评分/对位/模拟”的闭环跑通。

建议一期范围：

- 新增配将入口页或在账号页增加明显入口。
- 支持手动选择武将、战法和目标队数。
- 复用现有 `POST /api/v1/accounts/optimize` 生成最多 3 队共存阵容。
- 推荐结果展示评分、短板、冲突、未使用库存和资料上下文。
- 支持一键进入评分页、对位页或战报模拟。
- 保存推荐方案为普通阵容，沿用现有阵容管理和战报统计。

## 非目标

一期不做以下内容：

- 不做官方账号资产自动同步，不绕过登录、验证码、反爬或权限。
- 不做图片识别库存和截图 OCR。
- 不建立全赛季 meta 模板库作为唯一答案。
- 不对全量候选阵容做大规模模拟穷举排序。
- 不改造完整付费系统，只复用现有权益模型做次数或深度限制建议。
- 不承诺真实胜率，不声称复刻官方隐藏公式。

## 输入模型

一期可复用现有账号优化输入，并预留兼容字段：

```js
{
  generalIds: ["354732128524580868", "..."],
  tacticIds: ["367353731095738371", "..."],
  targetLineupCount: 3,
  scenario: "pk-default",
  season: "pk",
  catalogVersionId: "cv_...",
  options: {
    lockedGeneralIds: [],
    excludedGeneralIds: [],
    lockedTacticIds: [],
    excludedTacticIds: [],
    preferredTroop: "",
    strategyPreference: "balanced"
  }
}
```

字段说明：

- `generalIds`：用户拥有或参与推荐的武将 ID。
- `tacticIds`：用户拥有或参与推荐的战法 ID。
- `targetLineupCount`：目标推荐队伍数量，一期建议上限 3。
- `scenario`：评分场景，可复用当前评分场景。
- `season` / `catalogVersionId`：资料版本选择，必须与评分、对位和模拟保持一致。
- `locked*`：用户要求固定使用的武将或战法。
- `excluded*`：用户明确不想使用的武将或战法。
- `preferredTroop`：偏好兵种。
- `strategyPreference`：推荐偏好，例如均衡、输出、稳健、低战损。

## 输出模型

推荐接口输出应保持稳定结构：

```js
{
  catalogContext: {
    season: "pk",
    catalogVersionId: "cv_...",
    status: "published"
  },
  summary: {
    targetLineupCount: 3,
    generatedLineupCount: 2,
    averageScore: 84,
    confidence: "medium"
  },
  lineups: [
    {
      rank: 1,
      troop: "枪兵",
      generalIds: ["...", "...", "..."],
      tacticIds: ["...", "...", "...", "...", "...", "..."],
      score: 88,
      dimensions: {},
      weaknesses: [],
      reasons: [],
      alternatives: [],
      ruleCoverage: {},
      assumptions: []
    }
  ],
  conflicts: [],
  unused: {
    generalIds: [],
    tacticIds: []
  },
  warnings: []
}
```

关键要求：

- `lineups` 中每一队都能被评分页、对位页、模拟器直接消费。
- `conflicts` 必须告诉用户为什么某些库存无法共存。
- `warnings` 必须包含库存不足、资料版本、规则覆盖不足和估算边界。
- `catalogContext` 必须随结果返回，便于复盘。

## 页面与交互

### 入口

建议入口优先级：

1. 账号页增加“智能配将”卡片，适合从用户资产出发。
2. 评分页增加“从库存推荐阵容”入口，适合从评分能力出发。
3. 后续可评估是否增加底部 tab，但一期不强制增加。

### 页面结构

建议页面分为四段：

1. **库存与偏好**：选择武将、战法、赛季、目标队数、锁定/排除条件。
2. **生成按钮与状态**：显示可生成队伍数、库存完整度、API 模式提示。
3. **推荐结果**：按优先级展示阵容卡片、评分、短板、替代建议和可信度。
4. **后续验证**：保存阵容、去评分、去对位、跑模拟。

### 状态提示

- 库存少于 3 名武将或 6 个战法时，提示无法生成完整阵容。
- 多队共存无解时，返回可组队数和冲突原因。
- 规则覆盖不足时，提示推荐可信度下降。
- 远程 API 不可用时，提示用户切换远程模式或稍后重试，不清空已填库存。

## 接口与数据流

一期可复用现有链路：

```text
用户库存输入
  ↓
POST /api/v1/accounts/optimize
  ↓
utils/optimizer.js 生成候选阵容
  ↓
utils/scoring.js 评分与解释
  ↓
返回推荐阵容、冲突、未使用库存、资料上下文
  ↓
前台展示，并可跳转评分 / 对位 / 战报模拟
```

后续如果新增专用接口，建议保持与现有接口兼容：

- `POST /api/v1/lineups/recommend`：更直观的配将推荐接口名。
- 内部仍可调用 `optimizeLineups` 和 `analyzeLineup`。
- 旧的 `POST /api/v1/accounts/optimize` 保持兼容，避免破坏现有调用。

## 与现有能力联动

### 评分联动

配将推荐排序应复用 `utils/scoring.js` 的评分逻辑。推荐结果必须展示评分维度和短板，不能只输出阵容名单。

### 优化器联动

`utils/optimizer.js` 是一期基础能力。它已经具备库存组合、兵种选择、战法选择、多队共存、冲突与未使用库存输出。需求文档后续实现时应优先强化该模块，而不是重写推荐引擎。

### 对位联动

推荐阵容可以一键进入 `POST /api/v1/matchups/preview`，与环境模板或用户保存阵容做对位预览。对位结果作为验证建议，不作为一期推荐排序的硬依赖。

### 战报模拟联动

战报模拟适合二期增强：对 Top N 推荐阵容做批量模拟，输出胜率、平均剩余兵力、战损比和稳定性。模拟结果必须展示 `assumptions` 和 `ruleCoverage`。

### 资料版本联动

配将、评分、对位和模拟必须使用同一份资料上下文。生产环境会变化资料继续从数据库 published catalog snapshot 读取，静态 catalog 只能作为开发、测试或初始化 fallback。

## 权益与限制

权益策略待产品确认，本需求只给建议：

- 免费用户：基础配将、较少目标队数、有限生成次数、基础解释。
- 高级用户：更多目标队数、深度解释、更多替代方案、模拟复核、更多保存数量。
- 无论权益层级，都必须展示资料版本和估算边界。

## 验收标准

### 文档验收

- 文档清楚说明配将解决什么问题、一期做什么、不做什么。
- 文档包含输入模型、输出模型、页面结构、接口数据流和复用能力。
- 文档明确参考截图对应的是能力拆解，不臆造未确认 UI 细节。
- 文档没有写入生产密钥、token、服务器凭据。

### 功能验收

后续实现完成后，应满足：

- 用户录入至少 3 名武将、6 个战法后，可以生成至少 1 套推荐阵容。
- 库存足够时，可以生成最多 3 套不复用武将和战法的共存阵容。
- 推荐结果包含阵容优先级、武将、战法、兵种、评分、短板、可信度、冲突和未使用库存。
- 推荐阵容可以继续进入评分页、对位页或战报模拟入口。

### 接口验收

- 库存不足、战法不足、无解共存都返回稳定结构，不抛未处理错误。
- 响应包含 `catalogContext`，并记录资料版本。
- 后续扩展 `season`、`catalogVersionId`、锁定/排除条件时，不破坏旧请求。

### 解释验收

- 用户能看懂为什么推荐这队。
- 用户能看到主要短板和替代建议。
- 用户能看到规则覆盖、资料版本和估算说明。
- 推荐结果不使用“必胜”“官方最强”等绝对化文案。

## 风险与边界

### 算法性能

武将组合和战法组合数量会随库存增长快速膨胀。一期应继续采用现有组合枚举加贪心选战法策略，不做全量穷举最优解。

### 推荐质量

当前评分和模拟仍有估算边界，推荐应定位为“可解释方向建议”，不是唯一最优答案。

### 资料版本

不同赛季和资料版本会导致推荐变化。推荐结果必须记录资料上下文，方便用户复盘。

### 用户预期

“AI 配将”容易让用户期待全自动最强阵容。前台文案建议使用“智能配将建议”“可解释推荐”“基于当前资料和规则的方向判断”。

### 产品范围

不建议一期同时做图片识别、官方账号同步、全赛季 meta 模板、大规模模拟排序和付费系统重构。这些可以作为后续独立阶段。
